# 一、学习态度与人生方向

## 1.1 学习的底层要求（敢学 · 能学 · 会学 + 合作）

老师反复强调，进入 AI 行业最重要的不是技术，而是**学习态度**：

| 三大态度 | 含义（大白话） | 举例 |
|---------|---------------|------|
| 🆕 **敢学** | 见到新工具、新名词不退缩，敢上手试 | 看到 Claude、Cursor、Sora 第一反应是"我去试试"，而不是"好难" |
| 🔁 **能学** | 持之以恒，每天保证有知识增量 | 像老师每天讲课、日更小红书一样，把学习变成肌肉记忆 |
| 🧠 **会学** | 总结出适合自己的方法论 | 飞书做笔记 + 多维表格管资源 + AI 反查知识漏洞 |
| 🤝 **+合作** | 每周和同学聊各自项目，掌握一手信息 | 班里同学未来都是行业人脉，主动维护 |

> 💡 **小白补充**：AI 行业每周都有新东西（DeepSeek V4、Kimi K2.6、Claude 等），用"我不会就算了"的态度，半年就被淘汰。

## 1.2 笃定的人生方向（≠ 普通职业规划）

```
普通职业规划：先拿offer→进公司→升职→跳槽       ← 短期、被动
笃定的人生方向：清晰目标 + 强大愿力 + 坚定定力   ← 长期、主动
                  ↓ 以「年」为单位坚持做一件事
```

**举例**：老师每天讲课、日更小红书 → 这是以"年"为单位的坚持，最终积累了名气和私域流量。

## 1.3 工作发展时间表（卢老师建议）

| 时间节点 | 该做什么 | 目标 |
|---------|---------|------|
| **前 2-3 个月** | 工作的每一个月都去面试，了解市场行情 | 摸清自己的"手牌"和市场要求 |
| **3-6 个月** | 换面试到合适的工作 | 工资涨 30%，能学到更多项目 |

# 二、AI 行业趋势与就业方向

## 2.1 三大核心趋势

### 🔑 趋势一：模型能力趋同 → 竞争转向「数据 + 硬件」
- 现在 GPT、Claude、DeepSeek、Kimi 智商都差不多，**单纯比模型大小没意义了**。
- 真正决定胜负的是**数据质量** + **底层算力**。
- 比方：协和医院的医疗 AI 比别家强，因为它有几十年的病例数据。

- AI 不再只活在屏幕里，开始进入实体设备：机器人、汽车、按摩椅、AI 录音笔、AI 眼镜、AI 戒指…

- 美国卡显卡（英伟达 H100），中国必须搞自己的芯片（华为昇腾、寒武纪）。

# 第二篇 · AI 模型理论核心 🧠

# 四、什么是「模型」与「AI 模型」

## 4.1 传统模型（早就有的概念）

> **模型 = 对世界某种现象进行简化，总结规律，用于理解、解释、预测、决策**

🌰 **大白话举例**：

| 例子 | 这是什么模型 |
|------|------------|
| 天气预测 | 气象模型（总结大气规律预测明天下雨） |
| 一元二次方程 | 数学模型（用公式简化现实问题） |
| 算命/面相手相 | 经验模型（人类总结的"规律"） |
| 量化金融 | 金融模型（用数据预测股价） |
| 人脸识别 | 视觉模型（早期 AI，国内做得很好） |

**特点**：人工总结好规律 → 喂给模型 → 模型按规律工作（**呆板、机械化**）。

## 4.2 AI 模型（现代版进化）

> **AI 模型 = 不需要人工总结规律，模型从大量数据中自主学习总结**

```
       传统模型               AI 模型
        ┌───┐                 ┌───┐
人类 ─► │规律│ ─► 模型      数据 ─► │规律│ (自己总结)
        └───┘                 └───┘
                              ▲
                          AI 自己学
```

> 💡 **类比**：传统模型像背公式答题；AI 模型像学生看了几万道题，自己悟出解题思路。

## 4.3 AI 模型的两大核心特征

### 🎲 特征一：概率生成机制
模型回答你问题，**不是查字典**，而是**预测下一个词出现的概率，选概率最高的输出**。

🌰 你问"今天吃什么？"，模型内部是这样的：

| 候选词 | 概率 |
|--------|------|
| 火锅 | 35% ✅ 选这个 |
| 米饭 | 20% |
| 面条 | 15% |
| 沙拉 | 10% |

> 这就是为什么同一个问题，模型每次回答可能略有不同。

### 📦 特征二：知识压缩机制
模型学习时把海量数据**压缩成规律**存在"大脑"里。

> 类比：你读了 100 本历史书，最后大脑里不会记每一页，而是总结出"中国朝代更迭的规律"。

```
海量原始数据 (TB级)
    │ (压缩学习)
    ▼
模型参数 (几 GB - 几百 GB)
    │ (生成时调用)
    ▼
回答你的问题
```

## 4.4 AI 的三种学习方式（演进历程）

```
时间线 ─────────────────────────────►

  早期           中期            现在
   │              │              │
   ▼              ▼              ▼
规则模型      机器学习       深度学习 ⭐
(if-else)    (人总结规律)   (模型自主总结)
   │              │              │
   ▼              ▼              ▼
早期语音助手   天气预测       当前所有AI大模型
流水线视觉检测  股票模型      (GPT/Claude/Kimi等)
```

| 学习方式 | 工作原理 | 例子 | 缺点 |
|---------|---------|------|------|
| 🤖 **规则模型** | 写死的 if-else 规则 | 早期语音助手 | 死板，只会预设答案 |
| 📊 **机器学习** | 人总结特征规律告诉模型 | 天气预测、面容识别 | 还是依赖人 |
| 🧠 **深度学习** ⭐ | 模仿人脑，自己从数据学 | GPT、Claude、Kimi | 黑盒，不好解释 |

> 💡 **当前 AI 大模型 = 深度学习 + Transformer 架构**

### 🔬 扩展知识：什么是 Transformer？
Transformer 是 2017 年 Google 在论文《Attention is All You Need》中提出的神经网络架构，是当前**几乎所有大语言模型**（GPT、Claude、Gemini、Kimi、DeepSeek）的基础。

**核心机制**：自注意力机制（Self-Attention），让模型在处理一句话时，能"同时关注"所有词的关系。

🌰 **大白话**：你读"苹果从树上掉下来砸到牛顿"时，大脑会自动关联"苹果"和"砸"、"牛顿"和"砸"，Transformer 让 AI 也能这样做。

# 五、模型训练三大要素 ⭐⭐⭐

> 这是最重要的概念！记不住别的也要记住这个！

```
            模型训练 = 烹饪
            
   🔥 算力(GPU)    📋 算法(Transformer)    🥬 数据
        │                  │                  │
        ▼                  ▼                  ▼
      "燃料/微波炉"        "菜谱"            "原材料/菜"
        │                  │                  │
        └──────────────────┼──────────────────┘
                           ▼
                      🍳 训练好的 AI 模型
```

| 要素 | 类比 | 作用 | 现状 |
|------|------|------|------|
| 🔥 **算力（GPU）** | 燃料、微波炉 | 模型训练的"燃料" | 全国显卡使用量 **3 年内涨 30 倍** |
| 📋 **算法（架构）** | 菜谱 | 决定模型的学习方式（典型：Transformer） | 工程师负责设计 |
| 🥬 **数据** | 原材料、菜 | **核心！决定模型质量** | 国内英文数据稀缺，垂类数据是金矿 |

### 💡 金句：「对于模型来说，吃什么就拉什么。」
- 喂高质量数据 → 模型回答专业、准确
- 喂垃圾数据 → 模型胡说八道

> 这就是为什么**数据是 AI 训练师的核心工作**。

# 六、大语言模型（LLM）专题

## 6.1 什么是大语言模型？

> **定义**：基于深度学习技术，能够理解和生成人类语言的 AI 系统。通常具有 10 亿甚至数万亿参数，对海量文本数据进行学习，执行各种复杂任务。

### 目标演变

```
早期目标：让 AI 说话更像人  ──► 现在目标：帮人完成更复杂的工作任务
   (像 Siri)                      (像 24 小时助理)
```

## 6.2 大语言模型的「大」体现在哪？

| 维度 | 解释 | 数据 |
|------|------|------|
| 📐 **参数大** | 模型的"记忆容量"和"脑容量" | GPT-3: 750 亿；GPT-4: 据估万亿级 |
| 📚 **数据量大** | 喂全网海量文本 | 通常达数万亿 token 级别 |
| ⚡ **算力大** | 训练消耗能源巨大 | 训练 1 个大模型 ≈ **1400 万辆车全天运行** |

### 模型规模分类

```
小模型 (10B 以下)        中模型 (几十B - 100B)        大模型 (千亿以上)
   │                          │                            │
   ▼                          ▼                            ▼
GPT-Neo 7B                Llama 70B                    GPT-4 (估万亿级)
Qwen 7B                   Mixtral 8x22B                DeepSeek V4 (1.6万亿)
                          DeepSeek 67B                 Kimi K2 (1万亿)
```

> 💡 **B = Billion（十亿）**，所以 8B = 80 亿参数，100B = 1000 亿参数。

## 6.3 模型训练全流程

```

       │
       ▼

> 🎯 **AI 训练师在哪一步？** 主要在**数据准备 + 测试评估**两个环节。

## 6.4 TOKEN 是什么？（计费的最小单位）⭐

> **TOKEN = 模型处理文本的最小单位**

模型不直接处理"字"，而是把文字切成 token。

🌰 举例（英文）：
```
原文："I love AI"
切分：["I", " love", " AI"]
       3 个 token
```

中文大约：
- 1 个汉字 ≈ 1.5-2 个 token
- 1000 字 ≈ 1500-2000 token

### 计费规则

| 项目 | 说明 |
|------|------|
| 📥 **输入 token** | 你给模型的提问要算钱 |
| 📤 **输出 token** | 模型回答你的内容也要算钱 |
| 💰 **价格不同** | 不同模型每 1000 token 价格不同 |

> 🎯 **为什么按 token 计费？** 让用户更真实感知模型带来的价值。生成一篇软文花了 ¥0.05，你才知道 AI 创造了多少价值。

### 模型选型示例

做智能客服时不能盲选最贵的，要测试性价比：

| 模型 | 性能 | 价格（每 1000 token） | 适合场景 |
|------|------|--------------------|---------|
| GPT-4o | 顶级 | 较贵 | 复杂推理、关键业务 |
| Claude Sonnet | 顶级 | 中 | 长文本、写作 |
| GPT-4o mini | 中等 | 便宜 | 大量简单对话 |
| DeepSeek V3 | 较高 | 极便宜（约 1/10） | 个人开发者首选 |

# 八、环节①：需求承接（5W2H 法则）⭐⭐⭐

> ⚠️ **面试必考！** 5W2H 是 AI 训练师必须熟练掌握的需求分析框架。

## 8.1 5W2H 七问分析法

```
                        七问分析法 (5W2H)
                              │
        ┌─────────┬───────────┼───────────┬──────────┐
        ▼         ▼           ▼           ▼          ▼
      What       Why         Where       When        Who
     做什么    为什么做      在哪用    什么时候/节点   谁负责/使用
        │
        ▼
      How              How Much
   具体方法/步骤    多少成本/多少量(指标)
```

| 维度 | 含义 | 在 AI 项目中要明确 |
|------|------|-----------------|
| **What** | 做什么 | 任务目标，做什么数据集 |
| **Why** | 为什么做 | 业务背景，要解决的问题 |
| **Where** | 在哪用 | 应用场景（如打电话时判断意图） |
| **When** | 什么时候/节点 | 交付期限、关键节点、**预估排期** |
| **Who** | 谁负责/使用 | 需求方是谁、责任人是谁 |
| **How** | 具体方法 | 数据类型/数据量/准确率/标注规则 |
| **How Much** | 多少成本 | **预估预算**、人力成本 |

## 8.2 实战例子：汽车厂商购买意图分析项目

> **产品经理说**："要训练一个大模型能分析用户的购买意图，提升优化销售团队的成交。"

| 维度 | 答案 |
|------|------|
| **What** | 做一个能用于分析用户购买意图的数据集 |
| **Why** | 为了提高销售的成交量 |
| **Where** | 在打电话时就能判断用户需求，提高效率 |
| **When** | 什么时候交付一次，多久完成交付，预估排期 |
| **Who** | 我（AI 训练师） / 产品经理 |
| **How** | 数据类型 / 数据量 / 准确率 / 数据标注规则 |
| **How Much** | 多少成本，预估预算 |

## 8.3 沟通要点 & 留痕

| 要点 | 做法 |
|------|------|
| 📝 **沟通留痕** | 制作表单或填写问卷，确保需求明确，避免事后扯皮 |
| 🔄 **构建 SOP** | 若公司无相关流程，自行构建需求承接 SOP，提升工作效率 |
| ✅ **确认表单** | 必须沟通留痕，确认需求表单 |
| 📊 **数据文档检查** | 检查需求方提供的数据，避免"挂羊头卖狗肉" |

   └─ 找优秀的人答疑     ├─ 问题大的再培训  └─ 质检 10%-30%

【中期】我验收（正确率 95%-98%）

   ├─ 不合格 ──┬─ 计算需要多少数据二次质检
   │           ├─ 比如说差 20%，拿出来质检

## 10.2 人员构成与角色

| 人员类型 | 特点 | 适用场景 |
|---------|------|---------|
| 🏢 **内部实习生** | 大量线上实习生，成本低（智谱模式） | 中小项目 |
| 🌐 **众包平台** | 字节"魔豆众包平台" | 大批量、标准化 |
| 🤝 **供应商合作** | 外部人员，按人/按条计价 | 灵活补充人力 |
| 🏭 **标注基地（分公司）** | 专业团队 | 中大型项目 |

### 质检 / 标注人员配比

> 一般质检员：抽检 **10%-30%**；每人任务量 = 他能完成多少 × 80%（采集、喝水时间）

## 10.3 验收准确率与处理机制

| 准确率 | 处理方式 |
|--------|---------|
| ✅ **95%-98%（合格）** | 整体交付，撰写交付报告 |
| ⚠️ **不合格（如差 20%）** | 拿出来质检 → 二次质检直到达标 |
| ❌ **低于 60%或多次回扫不合格** | 重新找人做 |

## 10.4 人员汰换机制

> 一般累计**两次红牌**可替换，但不能随意换人。

| 阶段 | 处理原则 |
|------|---------|
| 🌱 **前期爬坡期** | 留余地，给培训机会 |
| 🌳 **稳定期** | 态度不认真、准确率低 → 适当替换 |

## 10.5 准确率奖励规则（实战经验）

| 准确率 | 计费规则（以单价 5 元/条为例） |
|--------|------------------------|
| ≥95% | 5 元 × 1.1 或 1.2（**奖励**） |
| 80-95% | 标准价 5 元/条 |
| 70-80% | 5 元 × 0.75（**打折**） |
| <70% | 不予结算（动态调整） |

> 💡 **金句**：「明确需求方验收的准确率，低于一定标准不给钱，促使对方卖力。」

## 10.6 后期交付流程

```

    │
    ▼

    │
    ├─ 项目信息（数据来源、用途）
    ├─ 人员标注量
    ├─ 质检量
    ├─ 合格率
    └─ 成本

# 十二、汽车购买意图项目带练（综合案例）

## 12.1 项目背景与需求

| 维度 | 内容 |
|------|------|
| 🎯 **背景** | 提升销售团队及公司销售能力，利用大模型语言理解能力，分析用户购买意图，优化销售团队话术，提高成交量 |
| 📁 **数据来源** | 销售团队与客户通话聊天记录（已筛选优质对话） |
| 📊 **数据量** | 10 条优质通话（每个 30-60 分钟） |
| 🎯 **准确率** | 95% |
| ⚠️ **限制** | 模型一次只能接受 2500 字以内 |

## 12.2 标注方案

```
标注方案三步走：

1. 由于模型一次只能接受 2500 字以内
   ↓ 对用户聊天记录做对话数据切分，确保在 2500 字内

2. 对用户回复中内容进行仔细阅读并标注
   ↓ 区分用户回答内容的购买意图强弱

3. 由于判断购买意图主观性过强
   ↓ 采取两人标注一条数据
```

## 12.3 标注规则（含示例）

### 切分规则

> 保证在 2500 字以内，并且切分时，切分点最好是和上一句无关，或在语气助词、停顿处。

| 数据示例 | 拆分点标注 |
|---------|----------|
| Q1: 帕拉梅拉真的降价了，现在是真的划算真不考虑？ | — |
| user: 降多少啊，你要跟我说个数啊，或者有没有打折？ | — |
| Q2: 这个你可以在店里聊啊。 | ✅ 切分点 |
| user: 我现在没空，等晚点吧 | — |

### 购买意图标注规则

| 强度 | 判定标准 | 示例 |
|------|---------|------|
| 🟢 **强意图** | 主动询价、谈优惠、约时间 | "降多少啊"、"什么时候到店" |
| 🟡 **中意图** | 有兴趣但需要考虑 | "我再考虑下"、"我跟家人商量" |
| 🔴 **弱意图** | 推脱、敷衍 | "我现在没空"、"再说吧" |

> 💡 **关键**：强、中、弱必须加解释和案例，案例必须来自真实作业。

| 🔌 **MCP 协议** | 调用其他软件工具（Chrome、Blender、3D 建模等） |

## 14.3 关键概念

### MCP（Model Context Protocol）= 上下文协议

> **作用**：统一了 APP 应用接口规范，让 Cursor 能调用其他软件工具。

```
       Cursor
         │
       MCP（桥梁）
         │
    ┌────┼────┐
    ▼    ▼    ▼
  Chrome Blender 飞书 ...
```

### CLI（Command Line Interface）

> 现在比 MCP 更常用，**权限终端更高**，可通过终端操控软件。例：用 Claude Code 操控飞书。

## 16.2 操作步骤

### Step 4：执行
- 回车后 Cursor 自动处理
- ⚠️ **注意操作权限**：避免文件误删

# 十七、提示词工程（PE / Prompt Engineering）

> 这是第二天下午的核心内容，也是和 AI 对话的"内功心法"。

## 17.1 提示词工程师（PE）岗位的由来

```
早期：模型能力不足
        │
        ▼
需要长串提示词约束生成结果
        │
        ▼
催生了"提示词工程师"岗位（PE）
        │
        ▼
现在：模型能力提升，但 PE 仍能让模型更精准理解需求
        │
        ▼
未来：CE（上下文工程师）→ 管理输入信息以优化输出
```

> 💡 **金句**：「提示词工程师岗位的出现，本质是因为之前模型能力不足，需要通过一大串提示词来约束模型生成结果，提升生成质量。」

## 17.2 系统提示词 vs 用户提示词

| 类型 | 特点 | 举例 |
|------|------|------|
| 🌐 **System Prompt（系统提示词）** | **全局性**，整个 APP 应用都用 | "你是一个客服助手，回答要专业礼貌" |
| 💬 **User Prompt（用户提示词）** | **指令精准**，针对具体任务 | "帮我写一封请假邮件，明天有事" |

## 17.3 优质提示词架构（IASCEF / CRISTE）

> 老师介绍了多种架构（IO、CRISTE、IASCEF），核心都是**结构化表达**。

### 通用 5 要素架构

```
┌─────────────────────────────────────────┐
│  1. 角色（Role）                         │
│     "你是一名资深的厨师"                  │
├─────────────────────────────────────────┤
│  2. 背景（Context）                     │
│     "我有一周食材，想做家常菜"            │
├─────────────────────────────────────────┤
│  3. 任务（Task）                        │
│     "请生成周一到周五的食谱"             │
├─────────────────────────────────────────┤
│  4. 要求（Requirement）                 │
│     "每天 3 餐，包含主食和蔬菜"          │
├─────────────────────────────────────────┤
│  5. 格式（Format）                      │
│     "用 Markdown 表格输出"               │
└─────────────────────────────────────────┘
```

## 17.4 提示词使用技巧（进阶）

| 技巧 | 说明 | 示例 |
|------|------|------|
| ✂️ **结构化表达** | 角色 + 背景 + 任务 + 要求 + 格式 | 见 17.3 |
| 📝 **Markdown 格式** | 用 #、-、1. 等定义标题列表 | 模型识别更准 |
| ✅ **肯定语气** | 用强制性指令强调重点 | "**必须回复中文**" |
| 🪜 **任务拆解** | 复杂任务拆成步骤 | "第一步...第二步..." |
| 📌 **末尾强调** | 重点后置或末尾总结 | 引起模型关注 |
| 🤔 **自我检查** | 不确定任务时让模型先罗列思路再执行 | "先告诉我你怎么做，确认后再执行" |
| ⚠️ **谨慎用示例** | 开放性任务不要给示例（会限制发挥） | 创新任务避免示范 |

## 17.5 实战例子：周一到周五食谱

❌ **差的提示词**：
> "帮我做食谱"

✅ **好的提示词**：
```
你是一位有 10 年经验的家庭厨师。
背景：我和家人 3 口人，希望做营养均衡的家常菜。
任务：请生成周一到周五的午餐食谱。
要求：
1. 每天有 1 个主食、1 个荤菜、1 个素菜
2. 荤素搭配合理，不重复
3. 食材容易在超市买到
格式：用 Markdown 表格输出，包含菜名、食材、烹饪时间
```

## 17.6 上下文工程师（CE）— 未来趋势

> **上下文（Context）的多种类型**：
> - 参考资料
> - 系统提示词（SP）
> - Memory 文档
> - 历史对话

⚠️ **关键认知**：模型输入内容**越多生成结果越烂**！

```
        ❌ 错误做法                    ✅ 正确做法
   把所有资料一股脑塞进去          只放精简、相关的信息
        │                              │
        ▼                              ▼
   注意力分散，结果差              聚焦目标，生成质量高
```

> CE 工作 = **管理上下文 + 瘦身（精简）**
